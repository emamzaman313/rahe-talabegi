# راهِ طلبگی — نسخهٔ اندروید و پشتیبانی آنلاین

این بسته، نسخهٔ توسعه‌پذیر اندرویدی «راهِ طلبگی» را بر پایهٔ HTML فعلی می‌سازد. فایل اصلی دسکتاپ و فایل کامل «راه‌دانِ نحو و صرف» در پوشهٔ `source/` حفظ شده‌اند؛ نسخهٔ اندرویدی از کپیِ جداگانهٔ `index.html` استفاده می‌کند تا افزودن ویژگی آنلاین به نسخهٔ آفلاین فعلی آسیب نزند.

## اکنون چه چیزی در کد وجود دارد؟

- صفحه‌های فعلی برنامه و راه‌دان در `index.html` حفظ شده‌اند.
- صفحهٔ پشتیبانی در اپ با ورود/ثبت‌نام ایمیلی، ارسال و دریافت پیام، فهرست پیام‌ها، وضعیت گفتگو و نمایش زندهٔ تغییرات اضافه شده است.
- `support-admin.html` یک پنل وب جدا برای کارشناس پشتیبانی دارد؛ تنها حسابی که در `app_metadata` نقش `support` دارد، با سیاست‌های RLS می‌تواند صندوق تمام گفتگوها را ببیند یا پاسخ دهد.
- `supabase/migrations/20261022000000_support_chat.sql` جدول‌ها، شاخص‌ها، triggerها، حداقل مجوزهای SQL، سیاست‌های RLS و تنظیم Realtime را تعریف می‌کند.
- داده‌های درسی/شخصی راه‌طلبگی همچنان در خود دستگاه و در ذخیره‌سازی فعلی HTML باقی می‌مانند. این بسته آن‌ها را بدون رضایت کاربر به سرور منتقل نمی‌کند. چت پشتیبانی یک دادهٔ جداگانه و آنلاین است.
- کدهای سرور فقط از کلید عمومی `publishable` در سمت کاربر استفاده می‌کنند. هیچ کلید `service_role` در برنامه قرار نداده‌ایم.

## ساخت و اجرای توسعه‌ای در ویندوز

پیش‌نیازها: Node.js نسخهٔ 22، npm، Android Studio با Android SDK نصب‌شده، و JDK 21 که با نسخهٔ Capacitor/Android Gradle Plugin سازگار باشد. برای ارتباط با Supabase نیز اینترنت و حساب Supabase لازم است.

1. فایل ZIP را از حالت فشرده خارج کن و PowerShell را در پوشهٔ `rahe-talabegi-mobile` باز کن.
2. اسکریپت `scripts/build-android.ps1` را اجرا کن. یا گام‌های زیر را دستی انجام بده.
3. فایل `.env.example` را به `.env.local` کپی کن و `VITE_SUPABASE_URL` و `VITE_SUPABASE_PUBLISHABLE_KEY` را با مقادیر پروژهٔ خودت جایگزین کن. اگر هنوز پروژهٔ Supabase نداری، ساخت و پیش‌نمایش ظاهر برنامه ممکن است ولی بخش چت پیام واقعی نمی‌فرستد.
4. در ترمینال اجرا کن:

   ```powershell
   npm install
   npm test
   npm run build
   npx cap add android
   npx cap sync android
   npx cap open android
   ```

5. Android Studio پروژه را باز می‌کند. ابتدا همگام‌سازی Gradle را کامل کن؛ سپس از منوی **Build → Build Bundle(s) / APK(s) → Build APK(s)** فایل APK آزمایشی بساز. برای دستگاه واقعی، USB debugging یا روش انتقال APK لازم است.

`android/` و فایل APK عمداً از این بسته جعل یا شبیه‌سازی نشده‌اند؛ این محیط Android SDK/Android Studio ندارد و نصب بسته‌های npm نیز به‌خاطر محدودیت شبکه تکمیل نشد. پوشهٔ اندروید واقعی را دستور `npx cap add android` روی کامپیوتر مجهز به SDK تولید می‌کند.

## راه‌اندازی سرور و چت پشتیبانی

### ۱. ساخت پروژهٔ Supabase

1. از [داشبورد Supabase](https://supabase.com/dashboard) پروژه بساز.
2. از مسیر Connect / API details مقدار Project URL و کلید Publishable را بردار و در `.env.local` بگذار. **کلید secret یا service_role را در فایل اپ نگذار.**
3. فایل `supabase/migrations/20261022000000_support_chat.sql` را در SQL Editor همان پروژه اجرا کن. اجرای این اسکریپت روی پروژهٔ اشتباه یا دیتابیسی که از قبل جدول هم‌نام دارد، بدون بازبینی انجام نشود.
4. جدول‌های `support_conversations` و `support_messages` با RLS ساخته می‌شوند. اسکریپت برای جدول‌های جدید، `GRANT`های صریح می‌دهد؛ این مهم است چون از ۳۰ اکتبر ۲۰۲۶ جداول جدید `public` دیگر لزوماً به‌صورت خودکار از Data API قابل دسترسی نیستند. اگر درخواست‌ها خطای `42501` یا خطای «table not exposed» دادند، بخش Data API/Exposed tables پروژه و مجوزهای صریح را بررسی کن؛ RLS جای مجوز جدول را نمی‌گیرد.
5. Realtime برای جدول‌های پیام و گفتگو فعال می‌شود، مشروط به اینکه publication استاندارد `supabase_realtime` در پروژه وجود داشته باشد.
6. با ایمیل خودت یک حساب کاربری بساز. تأیید ایمیل را طبق سیاست پروژه تنظیم کن؛ اگر تأیید فعال است، لینک ایمیل ممکن است ابتدا در مرورگر باز شود و بعد از تأیید باید دوباره در اپ وارد شوی. پیش از انتشار عمومی، URL بازگشت و روند بازیابی رمز عبور را برای دامنهٔ وب/لینک عمیق اندروید تنظیم و آزمایش کن.
7. برای اعطای نقش پشتیبانی، UUID حساب مورد اعتماد را در SQL Editor پیدا و از یک نشست مدیریتی امن، metadata سمت سرور را تنظیم کن. نمونه زیر را با UUID واقعی جایگزین کن؛ هرگز این عملیات را در برنامهٔ عمومی یا توسط کاربر عادی در دسترس نگذار:

   ```sql
   update auth.users
   set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb) || '{"role":"support"}'::jsonb
   where id = 'REPLACE-WITH-TRUSTED-SUPPORT-USER-UUID'::uuid;
   ```

   کاربر پشتیبان باید از حساب خارج و دوباره وارد شود تا JWT تازه نقش جدید را دریافت کند. نقش فقط از `app_metadata` خوانده می‌شود؛ `user_metadata` توسط خود کاربر قابل تغییر است و نباید مبنای اختیار باشد.
8. برای پاسخ‌گویی از همان پروژهٔ buildشده، صفحهٔ `support-admin.html` را در میزبانی وب باز کن و با حساب پشتیبانی وارد شو. در نسخهٔ محلی `npm run dev` نیز می‌توان مسیر `/support-admin.html` را باز کرد. انتشار واقعی این پنل باید پشت HTTPS باشد.

### نکات امنیتی ضروری

- برای پیام‌های پشتیبانی، متن خالی و بیش از ۵۰۰۰ نویسه رد می‌شود؛ متن کاربر پیش از نمایش HTML escape می‌شود.
- کاربر عادی فقط گفتگوهای خود را می‌بیند، نمی‌تواند وضعیت را تغییر دهد و اجازهٔ ویرایش/حذف پیام‌های ثبت‌شده ندارد.
- کارشناس می‌تواند گفتگوها را ببیند، پیام پاسخ بفرستد و وضعیت را تغییر دهد. تعیین این نقش فقط از سمت مدیر پروژه انجام می‌شود.
- ذخیره‌سازی HTML اصلی رمزنگاری حرفه‌ای نیست. اطلاعات عبادت، اخلاق، یادداشت‌ها و داده‌های حساس را بدون نیاز به سرور نفرست.
- این MVP اعلان Push در پس‌زمینه، ارسال فایل/تصویر، پنل گزارش‌گیری، سیستم تیکت چندکارشناس، محدودیت نرخِ اختصاصی و لینک عمیقِ نهایی برای تأیید ایمیل/بازیابی رمز را هنوز ندارد. قبل از استفادهٔ عمومی باید این موارد و تنظیمات Auth/SMTP/redirect بررسی شوند.

## آزمون‌ها و وضعیت

در این بسته با `npm test` آزمون‌های خالص JavaScript، اعتبارسنجی ورودی، نقش پشتیبانی، escaping متن، وجود سیاست‌های RLS و تنظیم صفحهٔ پشتیبانی اجرا می‌شوند. آن‌ها تست زندهٔ یک پروژهٔ Supabase نیستند. برای آزمون end-to-end باید migration در پروژهٔ واقعی اجرا شود و دو حساب جدا (کاربر عادی و پشتیبان) با هم آزمایش شوند.

برای آزمون نسخهٔ دسکتاپی اصلی و بازیابی پشتیبان، فایل‌های `source/rahe-talabegi-desktop.html` و `source/rahdan.html` همراه این بسته‌اند. فایل فعلی مستقل دسکتاپ نیز بدون تغییر در پوشهٔ جداگانهٔ تحویل نگه‌داری شده است.
